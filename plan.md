# SmartUstaz 3.0 — план технической модернизации

> Статус: **реализация начата в предоставленной базовой папке**. Зафиксированы baseline-аудит и frontend security review; подготовлен локальный AI gateway spike harness; добавлены первая Supabase schema/RLS migration, pgTAP-тесты, серверный каркас `ai-generate` с квотами/идемпотентностью, Auth-прототип и клиентский gateway transport. Supabase-проект не настроен; миграции, функция и реальный Auth/API не запускались; облачные документы не синхронизируются. Изменения не отправлялись в удалённый репозиторий.
>
> Репозиторий: https://github.com/ryouta-dev/SmartUstaz  
> Основная ветка на момент подготовки плана: `main`

## 1. Цель и принципы

Постепенно превратить SmartUstaz из браузерного приложения с локальным хранением и пользовательскими настройками AI API в облачный сервис для преподавателей, сохранив существующие функции и не переписывая приложение с нуля.

### Предпочтения проекта

- Размещение: облачный хостинг.
- ИИ: единый централизованный облачный API.
- Backend, авторизация и база данных: Supabase Auth + PostgreSQL.
- Первый мессенджер: Telegram.
- Бюджет: минимальный; использовать бесплатные квоты, где это разумно.
- Изменения: выполнять постепенно, небольшими проверяемыми этапами.
- Правило согласования: данный документ — план. Другие изменения кода, инфраструктуры и данных выполнять отдельно после согласования.

### Основные принципы

1. Сохранить текущий HTML/CSS/JavaScript frontend и существующее поведение.
2. Не переносить пользовательские данные в облако без понятного действия и подтверждения пользователя.
3. Никогда не помещать секретный ключ AI API, токен Telegram или Supabase service-role secret в браузер, публичный репозиторий или клиентские логи.
4. Применять принцип минимальных привилегий и проверять изоляцию пользовательских данных.
5. Проверять совместимость на реальном API и в реальном браузере, а не полагаться только на мок-сервер.
6. Избегать дорогостоящей инфраструктуры и преждевременного переписывания frontend.
7. Любой этап должен иметь критерии готовности и безопасный способ отката.

- `tests/transport.cjs`, `tests/generation.cjs`, `tests/smoke.cjs` — существующие автоматизированные тесты.

- `README.md`, `CHANGELOG.md` — документация проекта.

### Функции, которые нужно сохранить

- Генерация плана занятия, конспекта и слайдов.
- Компактная генерация комплекта и отдельное расширение конспекта/слайдов с подтверждением замены.
- Независимое сохранение готовых частей комплекта, если другая часть завершается ошибкой.
- Повторная генерация только отсутствующих частей и восстановление незавершённого комплекта.
- Сохранение ручных правок при повторных запросах.
- Импорт и анализ образцов/шаблонов.
- Редактирование результатов.
- Экспорт в PowerPoint и Word.
- Русский и казахский интерфейсы, язык материалов, светлая и тёмная темы.
- Мобильная навигация, статусы, обработка ошибок, отмена запросов и потоковый предпросмотр.
- Существующие ограничения на параллельные действия и защита от потери результата при ошибке.

### Выявленные риски и ограничения

1. **AI API вызывается из браузера.** `api-client.js` передаёт ключ в заголовке `Authorization`; сейчас пользователь задаёт API URL, ключ и модель. Для централизованного сервиса вызов нужно перенести на серверную сторону.
2. **Локальное хранение.** Материалы и настройки используют browser storage. Необходимо описать форматы данных перед миграцией, чтобы не потерять существующие документы.
3. **Большой `app.js`.** Не переписывать весь файл сразу. Выделять новые сервисы/модули постепенно, сохраняя существующие интерфейсы и тесты.
4. **Потенциальные XSS-риски.** Провести аудит всех мест, где данные пользователя, импортированных файлов или модели попадают в `innerHTML`/DOM. Использовать безопасные DOM API и корректное экранирование там, где HTML действительно нужен.
5. **Внешние CDN.** Word import/export зависит от клиентских библиотек, подключаемых извне. Проверить поведение при недоступности CDN, совместимость версий и лицензионные условия; по возможности зафиксировать версии и оценить локальное размещение.
6. **Реальный API не подтверждён текущими мок-тестами.** Нужны тесты с выбранным провайдером, его лимитами, форматом SSE и реальным временем ответа.
7. **Экспорт и браузеры.** Полностью проверить DOCX/PPTX, Safari/iOS, Chrome/Firefox и мобильный сценарий.
8. **Длительные запросы.** Текущий клиент допускает длительные операции (тайм-аут ожидания до 5 минут без активности и общий предел до 30 минут). Это может конфликтовать с ограничениями serverless-платформы; архитектуру генерации нужно подтвердить измерениями.

Существующие отчёты в `CHANGELOG.md` и `tests/last-run.json` описывают ранее выполненные проверки, но сами по себе не являются новым запуском тестов в рамках этого плана.

## 3. Целевая архитектура

### Предлагаемая схема

```text
Browser (existing HTML/CSS/JS)
  ├── Supabase Auth client
  ├── Existing generation UI and editor
  ├── Cloud document/template repository
  └── Calls authenticated Edge Functions
          ├── ai-generate
          │     ├── validates session, input and quota
          │     ├── calls one centrally configured AI provider
          │     └── records job status and result
          ├── telegram-link
          │     └── securely binds Telegram identity to a signed-in account
          └── telegram-webhook
                ├── validates webhook secret and payload
                └── reuses shared generation service
Supabase
  ├── Auth
  ├── PostgreSQL + Row Level Security (RLS)
  ├── Edge Functions
  └── secrets / logs
External hosted AI API
Telegram Bot API
```

### Компоненты

- **Frontend:** оставить обычный HTML/CSS/JavaScript. Не мигрировать на React только ради добавления аккаунтов.
- **Hosting:** можно сохранить GitHub Pages для статического frontend, если текущая публикация подходит. Frontend не должен содержать секреты.
- **Auth:** Supabase Auth — регистрация, вход, сессия, выход и восстановление доступа.
- **Database:** PostgreSQL в Supabase для документов, шаблонов, профилей и состояния генерации.
- **Backend:** Supabase Edge Functions для AI-шлюза, безопасной привязки Telegram и webhook.
- **AI:** один централизованно выбранный облачный провайдер и модель; конфигурация хранится только на сервере.
- **Telegram:** бот запускает разрешённые действия и сообщает о статусе/результате; редактирование и экспорт остаются в веб-приложении.

### Ограничение serverless и обязательный технический spike

У Supabase Edge Functions есть ограничения длительности и ожидания ответа. По официальной документации, для hosted Edge Functions wall-clock limit составляет 150 секунд на Free и 400 секунд на платном плане; request idle timeout — 150 секунд, после чего может вернуться 504, если функция не отправляет ответ. См. [официальные лимиты Edge Functions](https://supabase.com/docs/guides/functions/limits).

Так как текущая генерация может включать несколько этапов и допускать долгие ожидания, **нельзя заранее гарантировать, что один синхронный вызов Edge Function подойдёт**. На этапе прототипа нужно измерить длительность и проверить потоковую передачу.

Варианты:
1. Если реальный ответ стабильно укладывается в лимиты — Edge Function с корректным streaming.
2. Если запрос слишком долгий — перейти к схеме задач: быстро создать `generation_jobs`, обрабатывать задачу через подходящий worker/очередь и возвращать клиенту статус/частичный результат.
3. Если для нужного streaming/background workflow Edge Functions недостаточно — рассмотреть отдельный небольшой backend/worker. Это запасной вариант, а не исходное требование.

Не запускать платный backend, пока измерения не покажут необходимость.

## 4. Схема базы данных

Начальная схема должна оставаться небольшой. Поля ниже — проектное предложение, уточняемое после аудита реальных форматов локальных данных.

### `profiles`

- `id uuid primary key references auth.users(id) on delete cascade`
- `display_name text`
- `locale text` (например, `ru` или `kk`)
- `created_at timestamptz`
- `updated_at timestamptz`

### `documents`

- `id uuid primary key`
- `user_id uuid not null references auth.users(id)`
- `title text not null`
- `topic text`
- `document_type text not null` — например, план, конспект, слайды или комплект
- `content jsonb not null` — структурированный контент после проверки текущих форматов
- `status text` — например, draft/ready/partial; согласовать конечный enum
- `created_at timestamptz`
- `updated_at timestamptz`
- при необходимости `version integer` или отдельная таблица версий

### `templates`

- `id uuid primary key`
- `user_id uuid not null references auth.users(id)`
- `name text not null`
- `template_type text not null`
- `content jsonb not null`
- `created_at timestamptz`
- `updated_at timestamptz`

### `generation_jobs`

- `id uuid primary key`
- `user_id uuid not null references auth.users(id)`
- `status text not null`
- `document_id uuid null references documents(id)`
- `error_code text null`
- `created_at timestamptz`
- `started_at timestamptz null`
- `finished_at timestamptz null`
- при необходимости безопасные поля для типа операции и количества использованных токенов

Не записывать секреты, полные заголовки авторизации или ненужный чувствительный контент. Хранение полного промпта для диагностики не включать по умолчанию.

### `telegram_links`

- `user_id uuid primary key references auth.users(id) on delete cascade`
- `telegram_user_id bigint unique not null`
- `linked_at timestamptz not null`

Для привязки аккаунта может понадобиться отдельная таблица одноразовых токенов с хешем токена, сроком действия и отметкой использования. Токены должны иметь короткий срок жизни и быть одноразовыми.

### RLS и доступ

- Включить RLS на всех таблицах с пользовательскими данными.
- Пользователь читает и изменяет только собственные документы и шаблоны.
- Для `generation_jobs` разрешить пользователю читать только собственные задачи; создание/изменение статуса контролируется серверной логикой.
- Для `profiles` разрешить безопасное чтение и обновление только собственного профиля.
- `telegram_links` менять только через проверенную серверную процедуру/функцию, чтобы нельзя было присвоить чужой Telegram ID.
- Проверить не только политики RLS, но и SQL grants.
- Никогда не использовать service-role secret на клиенте.
- Добавить индексы по `user_id`, `updated_at`, `status` там, где они оправданы запросами.

На MVP не добавлять сложные роли организаций, совместные библиотеки и публичные ссылки на документы, пока пилот не подтвердит необходимость.

Документация: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 5. Миграция локальных данных

Миграция должна быть явной и обратимой. Нельзя стирать browser storage автоматически после входа или успешной синхронизации.

1. Инвентаризировать все ключи `localStorage`/`sessionStorage`, схемы объектов, шаблоны и результаты генерации.
2. Добавить экспорт локальных данных в JSON до внедрения облачного хранения.
3. После входа показать пользователю, какие локальные материалы найдены, и предложить импорт.
4. Валидировать JSON, типы полей, размеры файлов/записей и количество объектов.
5. Переносить пакетами; отображать успешные и неудачные записи.
6. Использовать стабильные ID или таблицу соответствия для безопасного повторного импорта без дублей.
7. При совпадении локального и облачного документа не перезаписывать его молча. Предложить сохранить обе версии или выбрать версию.
8. Оставить локальную резервную копию до явного подтверждения пользователя.
9. Обеспечить повтор импорта после сетевого сбоя без создания неконтролируемых дублей.
10. Протестировать пустое, частично повреждённое и большое локальное хранилище.

### Разделение данных

- Облачные: документы, шаблоны и состояние генерации, которые должны быть доступны с нескольких устройств.
- Локальные: тема, язык интерфейса и временные UI-настройки, если синхронизация для них не нужна.
- Секреты: не хранить AI API key в браузере. После миграции удалить пользовательскую настройку ключа из интерфейса; старый ключ не переносить в Supabase.

## 6. Единый облачный AI API

### Новый поток запроса

1. Преподаватель авторизуется и запускает генерацию.
2. Frontend отправляет параметры в функцию `ai-generate`.
3. Сервер проверяет сессию, разрешённый тип операции, размер входных данных и квоты.
4. Сервер формирует запрос к централизованно настроенному провайдеру.
5. Ключ API берётся из server-side secret.
6. Результат и статус задачи сохраняются; frontend отображает поток/результат.
7. Ошибка одного элемента комплекта не уничтожает уже успешно созданные разделы.

### Изменения UI

Убрать из пользовательских настроек:
- произвольный Base URL;
- поле API key;
- выбор model ID;
- опцию сохранения API key в localStorage;
- пользовательское переключение AI-провайдера.

Вместо этого показать:
- состояние доступности AI-сервиса;
- статус генерации;
- понятные сообщения об ошибке;
- квоту/ограничения, если это необходимо пользователю.

Администратор конфигурирует провайдера и модель на сервере. Публичные Supabase URL и publishable key могут использоваться в клиенте только при корректных политиках доступа; секретный ключ AI и Supabase service-role key должны оставаться серверными.

### Защита от расходов и злоупотреблений

- Лимит частоты запросов и одновременных задач на пользователя.
- Ограничение размера входного текста и файлов.
- Ограничение максимального ответа/токенов.
- Квота генераций или токенов за период.
- Общий аварийный лимит затрат и возможность быстро отключить генерацию.
- Не делать автоматический повтор запроса, если он может повторно списать стоимость.
- Идемпотентность создания задач и обработка повторных запросов.
- Логи без секретов и избыточного контента.
- Ясное сообщение при достижении квоты.

Единый API не означает бесплатный API. Точную модель и провайдера выбрать после проверки качества русского/казахского языка, поддержки SSE, лимитов, стоимости и политики хранения данных. На пилоте ограничить число пользователей и расходы.

### Сохранение поведения

Новый транспорт должен сохранить:
- streaming SSE и fallback на JSON, если он нужен провайдеру;
- отмену запроса;
- тайм-ауты и понятные коды ошибок;
- обнаружение обрезанного/неполного ответа;
- частичный успех комплекта;
- повтор только недостающих разделов;
- сохранение ручных правок;
- запрет на автоматический повтор, способный удвоить расходы.

## 7. Telegram-интеграция

### MVP-команды

- `/start` — приветствие и подключение аккаунта.
- `/help` — доступные команды.
- `/new` — пошаговый запуск генерации с темой и параметрами.
- `/status` — статус последней задачи.
- `/open` — ссылка на веб-приложение для редактирования и экспорта.

В первой версии не дублировать весь редактор и библиотеку внутри Telegram. Полноценное редактирование и экспорт остаются на сайте. Длинные материалы лучше выдавать ссылкой на документ или небольшим резюме, а не отправлять одним огромным сообщением.

### Безопасная привязка

1. Пользователь входит на сайт.
2. Нажимает «Подключить Telegram».
3. Сервер выдаёт случайный одноразовый токен с коротким сроком действия.
4. Пользователь отправляет токен боту.
5. Backend проверяет токен и привязывает числовой Telegram user ID к текущему аккаунту.
6. Токен помечается использованным и больше не принимается.

Не использовать Telegram username как идентификатор: он может меняться. Защитить привязку от повторного использования токена, перебора, чужого аккаунта и гонок.

### Webhook и повторные события

- Только HTTPS endpoint.
- Проверять секретный заголовок Telegram webhook и валидировать входной payload.
- Не доверять переданному из сообщения user ID как доказательству владения аккаунтом.
- Проверять связь Telegram ID с `telegram_links`.
- Применять те же квоты и разрешения, что и на сайте.
- Обрабатывать повторную доставку события идемпотентно.
- Не отправлять в логи токены привязки, токен бота или полные секретные заголовки.

Документация: [Telegram Bot API](https://core.telegram.org/bots/api).

## 8. Этапы реализации и критерии готовности

Оценки ниже предварительные для одного разработчика, использующего AI coding agents. Это не гарантия сроков; этапы могут занять больше времени при выявлении дефектов.

### Этап 0 — аудит и фиксация исходного состояния (ориентир: 1–2 дня)

Работы:
- Зафиксировать текущий commit и резервную копию.
- Запустить `npm test` и сохранить отчёт.

Критерии готовности:

### Этап 3 — AI-шлюз и проверка длительных запросов (ориентир: 2–4 дня)

- Добавить квоты, лимиты, обработку ошибок и безопасные логи.
- Проверить реальный API, SSE/JSON, отмену и длительные запросы.
- При необходимости реализовать схему задач/worker вместо одного долгого HTTP-запроса.

Критерии готовности:
- Пользователю не нужен собственный API key.
- Секрет отсутствует в bundle, клиентских запросах и браузерном хранилище.
- Основные сценарии генерации проходят на реальном провайдере.
- Время ответа соответствует лимитам выбранной инфраструктуры.

Критерии готовности:
- Материалы доступны на двух устройствах.
- Не происходит молчаливой перезаписи.

- Повторный импорт не создаёт неконтролируемые дубликаты.

### Этап 5 — Telegram (ориентир: 2–4 дня)

Работы:

Критерии готовности:

## 9. Предлагаемая структура проекта после модернизации

Это целевая структура, а не описание существующего дерева. Менять структуру только по мере реализации соответствующих этапов.

```text
SmartUstaz/
├── index.html
├── app.js
├── api-client.js
├── styles.css
├── vendor/
├── tests/
├── supabase/
│   ├── config.toml
│   ├── migrations/
│   │   ├── 0001_profiles.sql
│   │   ├── 0002_documents.sql
│   │   ├── 0003_templates.sql
│   │   ├── 0004_generation_jobs.sql
│   │   └── 0005_telegram_links.sql
│   ├── functions/
│   │   ├── ai-generate/
│   │   ├── telegram-webhook/
│   │   └── telegram-link/
│   └── tests/
├── docs/
│   ├── architecture.md
│   ├── migration-plan.md
│   └── deployment.md
└── package.json
```

Точные имена функций, таблиц и миграций могут измениться после прототипа. Не создавать пустые каталоги/миграции только ради соответствия схеме.

### Git workflow

1. Работать в feature-ветке, не разрабатывать прямо в `main`.
2. Каждую SQL-миграцию хранить в Git.
3. Сначала тестировать локально и на тестовом Supabase-проекте.
4. Запускать `npm test`, новые тесты RLS и ручные браузерные проверки.
5. Проверять diff и не коммитить `.env`, токены, дампы или персональные данные.
6. Объединять изменения в `main` только после проверок.
7. Публикацию и переключение пользователей проводить отдельно от изменения схемы.

## 10. Бюджет и эксплуатация

| Компонент | Стартовый вариант | Риски/заметки |
|---|---|---|
| Frontend | GitHub Pages | Статический frontend; секретов в нём быть не должно |
| Auth + PostgreSQL | Supabase Free для прототипа | Проверять актуальные квоты, правила паузы проекта и условия резервного копирования |
| Backend | Supabase Edge Functions | Проверить длительность AI-запросов и ограничения streaming |
| AI | Один централизованный API | Основной переменный расход |
| Telegram | Telegram Bot API | Нужен публичный HTTPS webhook и безопасный токен |
| Домен | Отложить | Добавить при необходимости собственного адреса |

До начала пилота:
- Установить максимальный бюджет на AI API.
- Настроить квоты пользователей и аварийное отключение.
- Измерить среднюю стоимость типового комплекта.
- Не обещать пользователям неограниченную генерацию.
- Проверить актуальные цены и ограничения сервисов перед развёртыванием.

Документация Supabase меняется; перед запуском проверять актуальные лимиты:
- [Edge Functions — Limits](https://supabase.com/docs/guides/functions/limits)
- [Edge Functions — Pricing](https://supabase.com/docs/guides/functions/pricing)
- [Edge Functions](https://supabase.com/docs/guides/functions)

## 12. Рекомендуемый порядок

1. Зафиксировать текущую версию, запустить тесты и провести аудит безопасности.
2. Создать тестовый Supabase-проект, схему БД и проверить RLS.
3. Сделать технический прототип AI-шлюза и проверить реальный API/streaming.
4. Подключить Auth, облачные документы и безопасный импорт локальных данных.
5. Реализовать Telegram и провести пилот с небольшой группой преподавателей.
6. Выбирать следующие функции по обратной связи преподавателей, а не по предположениям.

**Главный технический приоритет — безопасный серверный AI API и сохранение надёжности текущей генерации.** Авторизация и Telegram должны строиться поверх этой основы, а не заменять её.

## 13. Вне текущего объёма

Не делать в первой версии:
- полного переписывания frontend на новый framework;
- нескольких AI-провайдеров с пользовательским выбором;
- локального AI-моделя как единственного production backend;
- WhatsApp-интеграции до проверки Telegram-пилота;
- сложной системы организаций, совместного редактирования и публичных документов;
- автоматического удаления локальных материалов;
- платной инфраструктуры до измерения реальной необходимости.

Эти решения можно пересмотреть после пилота и оценки расходов.
